# 0017. 場所の業種は機械可読な code を正としてマスタに正規化する（v13）

- Status: Accepted
- Date: 2026-08-15

関連: Google 由来データを別テーブルに分けた判断は [0001](0001-place-data-separation.md)。
自動命名の課金方針は [0014](0014-place-naming-cost-policy.md)（この ADR はその一度きりの例外を含む）。

## Context（背景）

地図のマーカーを「どんな場所か」で描き分けたい（カフェ／公園／飲食店…）。そのためには
**場所の業種を判定に使える形で持っている**必要がある。

ところが v12 までの `google_places.category` には、Places の `primaryTypeDisplayName`
＝ **「カフェ」という表示用の文字列**が入っていた。これには 2 つの問題がある。

1. **ロケール依存**。表示名は端末の言語設定で変わる。これを手掛かりにアイコンを出し分けると、
   言語を変えた瞬間に全部の判定が外れる。
2. **重複**。同じ業種の場所の数だけ同じ文字列が並ぶ。業種は場所の属性ではなく、場所が参照する
   独立した概念になっている。

Places SDK は同じ呼び出しで**機械可読な `primaryType`（`cafe`）**も返せる。既に
`PRIMARY_TYPE_DISPLAY_NAME` を要求しており、`PRIMARY_TYPE` は同じ課金区分（Pro）なので
**追加で要求しても単価は変わらない**。

## Decision（決定）

**`google_place_categories` を新設し、`google_places` はその id を参照する。判定は `code` で行う。**

- `google_place_categories(id, code UNIQUE, displayName)`。`code` が Places の `primaryType`。
  **id はサロゲート**（`places` / `stops` / `wishlist` と揃える）で、業種の同一性は `code` の
  UNIQUE 索引が担保する。
- `google_places.category`（表示名）は**廃止**し、`categoryId` の外部キーに置き換える。
- 行は**事前にシードしない**。Places の応答で出会った業種だけを都度 upsert して育てる。
- ドメインでは `PlaceCategory(code, displayName)` として扱う。**表示名だけあって code が無い状態は
  作らない**（業種が取れなければカテゴリそのものを持たない）。
- **アイコンなどの表示の対応付けは DB に持たず、コード側に置く**。

### 既存データの移行

既存行は表示名しか持たず、「カフェ」から `cafe` を復元するのは推測になる。よって
**マイグレーションでは列ごと捨て、Google から業種を引き直して埋めた**
（一度きりの Worker）。これは [0014](0014-place-naming-cost-policy.md) の
「place 1 件 1 回」に対する**一度きりの例外**であり、恒久的な仕組みではない。

利用者が 1 人なので、**流し切ったことを確認してから Worker ごと削除した**（実施・削除とも 2026-08-16）。
以後この経路で業種が埋まることはなく、v13 より後に解決した場所だけが業種を持つ。

## Alternatives（検討した没案）

- **表示名（`category`）のまま、日本語のキーワードで判定する** … 「カフェ」を含むなら喫茶アイコン、
  のような対応表。実装は要らないが、**ロケールを変えると全滅**し、Google の表記ゆれにも耐えない → 却下。
- **`code` を主キーにする（サロゲート無し）** … 正規化としては素直だが、他テーブルが軒並み
  `id` のサロゲートキーで揃っている中でここだけ自然キーになる。将来 code を振り直したくなったとき
  参照側を全部書き換える羽目になる → 却下。
- **`category` 列を残したまま `categoryId` を足す** … 何も失わないが、表示名が 2 か所にある状態が
  残り、正規化の目的が半分しか達成されない → 却下。
- **表示名を捨て、`code` だけ持って画面には自前の和名を書く** … マスタが 1 列で済むが、Google の
  業種は数百あり、出会うたびに和名を足す作業が発生する。表示名は応答に付いてくるので持つ方が安い → 却下。
- **アイコンの分類（FOOD / PARK …）もテーブルに持つ** … データ駆動にはなるが、`R.drawable` の ID は
  DB に入れられず結局コードで分岐する。対応を変えるたびにマイグレーションが要るだけ → 却下。
- **移行時に既存の表示名を「code 未確定」の行として残す** … 一覧のカテゴリ表示は途切れないが、
  code が NULL の暇行が残り、同じ業種が「暫定行」と「正式な行」に二重化する → 却下。引き直す方を採った。

## Consequences（結果・トレードオフ）

- 業種の判定が**言語設定に依存しなくなる**。地図のアイコン出し分け（この ADR の目的）が成立する。
- 表示名の重複が消え、Google 側の表記が変わったときの追随が 1 行の更新で済む。
- 読み取りに**結合が 1 つ増える**（`google_places → google_place_categories`）。件数は業種の種類数で、
  場所の数には比例しないので実害は小さい。
- 移行時に**既存の場所の数だけ Place Details（Pro）を 1 回ずつ**呼ぶ。以後は増えない。
- 業種を持たない POI（`primaryType` が無い地点）は、移行後もカテゴリ無しのまま残る。バックフィルは
  済んで削除したので、**この先カテゴリが埋まるのは新しく解決した場所と、手動で取り直した場所だけ**。
- **ユーザーが自分で編集できるカテゴリを、あとから並べて足せる**。この ADR の業種は「Google が
  その施設をどう分類しているか」＝施設の属性なので `google_places` 側に置いた。自分の分類は
  ユーザー入力なので `places` 側に `place_categories` を作って足す形になり、
  [0001](0001-place-data-separation.md) の分け方をそのまま踏襲できる。テーブル名を
  `google_place_categories` にして `place_categories` を空けてあるのはこのため。構想は
  [roadmap](../roadmap.md) の「温めている案」。
- 移行のための暫定コードは**残っていない**（Worker・`fetchCategoryOnly`・`getWithoutCategory`・
  起動時の予約を削除済み）。同じことをもう一度やるなら書き直しになるが、一度きりの処理を
  残し続けるより、必要になったときに書く方を選んだ。
