# 0025. ひとつの Google 施設を持てる場所は 1 つだけにする（v16）

- Status: Accepted
- Date: 2026-08-31

関連: 同一性の決め方は [0023](0023-place-identity-and-coordinate-anchor.md)、ID での同定は
[0006](0006-place-identity-by-googleplaceid.md)、非破壊の原則は
[0012](0012-non-destructive-reanalysis.md)。由来（`DETECTED`/`USER`）の扱いは
[../designs/places.md](../designs/places.md)。

## Context（背景）

`google_places.googlePlaceId` に制約が無く、**同じ施設を 2 つの place が持てる**。

`getPlaceIdByGoogleId` は 1 件しか返さないので、この状態になると「この施設の場所はどれか」の
答えがブレる。POI からの立ち寄り追加や誤検知の選び直しが、日によって別の place に付き、
同じ施設への訪問がばらける。

二重になる経路は 2 つある。

**① 自動の解決（経路詳細の「場所を取得」・オンライン復帰後のキャッチアップ）**

広い敷地では、同じ施設の別の位置で place ができる（アンカーが 30m 以上離れるため別扱い）。
[0023](0023-place-identity-and-coordinate-anchor.md) で「解決後に `googlePlaceId` で統合する」
仕組みを入れたが、寄せてよい条件を **`source == DETECTED` かつ中身が空**としていた。
そのため、地図の空き地点から手で足した place（`USER` になる）は、名前もメモも付けていなくても
寄せられず、素通りして二重になっていた。

**② 明示の紐付け（場所詳細の「Googleで情報を取得」）**

空き地点として登録した場所に、あとから施設を選ぶ経路。他の place が既に持っている施設でも
選べてしまう。地図の POI をタップして登録した場合は ID 同定で既存が再利用されるので起きない。
起こりうるが頻度は低い。

## Decision（決定）

**`google_places.googlePlaceId` を UNIQUE にする（v16）。** そのうえで、二重になりかけたときの
振る舞いを経路ごとに決める。

### 寄せる条件から由来を外す

同じ施設と分かったとき、**中身が空なら寄せる**。判定から `source` を落とす。

```text
これまで: source == DETECTED かつ 名前なし・メモなし・行きたいなし・訪問済みなし
これから:               名前なし・メモなし・行きたいなし・訪問済みなし
```

`USER` は「**自動回収から守る**」ための印であって、施設が同じと分かったときに寄せない理由ではない。
手で足しただけで何も入れていない place は、寄せて困らない。これで ① のほとんどが自動で片付く。

寄せたあと、寄せる側が `USER` だったら**寄せ先も `USER` に昇格**させる。印を落とすと、まとめた
結果が自動回収の対象に戻ってしまう。

### 寄せられないときは、施設情報を付けずに残す

自分で名前・メモを入れた place、行きたい・訪問済みの印が付いた place は勝手に寄せられない。
その場合は **place をそのまま残し、施設情報だけ付けない**。

- **① 自動**は黙って見送る。バックグラウンドやボタン一つで何件も走るので、そこで確認は出せない。
  解決記録（`place_resolutions`）は残して、同じ問い合わせを繰り返さない。
- **② 明示**は紐付けを断り、**理由を画面に出す**（「同じ施設の場所が既にあるため、施設情報は
  紐付けませんでした」）。名前・メモなど他の編集はそのまま保存する。

### 既存の重複は v16 で片付ける

同じ `googlePlaceId` の行が複数あれば、**最も古い 1 件だけ**を残して他の行を消す。
**place そのものは消さない**（名前・メモ・行きたいを守る）。施設情報だけ落ち、以後は先にある
場所が施設を持ち続ける。解決記録も消さない（消すと自動命名がまた同じ施設を引いて、また断られる）。

### `@Insert(onConflict = REPLACE)` をやめる

REPLACE は削除してから入れ直すので、UNIQUE にぶつかった行を**黙って消して**別の place に
付け替えてしまう。`@Upsert` に変える。主キー（`placeId`）の衝突だけが更新になり、施設の重複は
エラーになる。書く前に `getPlaceIdByGoogleId` で確かめるのは呼び出し側の責任。

## Alternatives（検討した没案）

- **UNIQUE を付けない（現状維持）** … 二重を許すと `getPlaceIdByGoogleId` の答えがブレ続ける。
  同じ施設への訪問がばらける原因がアプリ側に残る → 却下。
- **衝突したら常にまとめる（確認なし）** … 別々に名前・メモ・行きたいを付けた 2 件が、黙って
  1 つになる。[0012](0012-non-destructive-reanalysis.md) の「検出は事実を出すだけ、解釈は
  ユーザーがする」に反する → 却下。
- **① でも「まとめますか?」と聞く** … 「場所を取得」は 1 回で何件も解決するので、確認が連続して
  出る。押し切るまで何も進まない → 却下。
- **衝突した place を自動で消す** … ユーザーが入れた名前・メモが消える。施設情報が付かないだけ
  なら実害は小さい → 却下。

## Consequences（結果・トレードオフ）

- **「何度取得しても施設情報が付かない場所」ができる**。衝突した place は「未取得」に出続け、
  ボタンを押しても付かない。理由が画面に出るのは ② だけで、① は黙って見送る。
- **まとめる手立てがまだ無い。** 「同じ施設の場所が 2 つある」と分かっても、手で 1 つにできない。
  place の統合（名前・メモ・行きたい・訪問済みの引き継ぎ）は別の塊なので、ロードマップに送る。
- 由来を見なくなったぶん、**手で足しただけの place は自動でまとまる**。意図して分けたい場合は、
  名前かメモを入れておけば寄せられない。
- v16 のマイグレーションで、既存の重複のうち古くない方から施設情報が落ちる。place と立ち寄りは
  残るので、記録そのものは失われない。
