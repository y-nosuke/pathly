# Issue・ADR・ドキュメントの住み分け

「これからやること」は Issue、「決めたことの理由」は ADR、「今どうなっているか」は仕様・設計に書く。
同じことを 2 か所に書かない。

---

## どこに何を書くか

| 置き場所                                      | 書くこと                                     | 時間の向き       | 終わり方                         |
| --------------------------------------------- | -------------------------------------------- | ---------------- | -------------------------------- |
| [requirements.md](../requirements.md)         | 「こうしたい」という要望（なぜ作るか）       | ずっと残る根っこ | 基本的に消さない                 |
| [roadmap.md](../roadmap.md)                   | フェーズと大きな方向・進捗（Issue へリンク） | これから（大）   | フェーズごとに更新               |
| **Issue**                                     | 個々の作業・不具合・調査・アイデア           | これから（小）   | PR のマージで閉じる              |
| **PR**                                        | 実装                                         | 今               | マージ                           |
| [adr/](../adr/)                               | 設計上の判断と理由・採らなかった案           | 過去             | 残し続ける（覆したら置き換える） |
| [specs/](../specs/) / [designs/](../designs/) | 今どうなっているか                           | 現在             | 実装に合わせて更新               |

## 流れ

```
要望（requirements.md）
  → Issue を立てる（背景・やること・完了の条件）
    → Issue の中で方針を検討する
      → 設計上の判断が要るなら ADR を書く
    → PR（本文に Closes #番号）→ マージで Issue が自動で閉じる
  → specs / designs を今の姿に更新する
```

- **すべての Issue に ADR が要るわけではない。** 後で「なぜこうなっているのか」と聞かれそうな判断だけ ADR にする。
  不具合の修正や小さな追加は Issue と PR で足りる。
- **Issue を閉じても、判断の理由は ADR に残る。** Issue のコメントは探しにくいので、残すべき理由は ADR へ移す。
- **roadmap には作業の中身を書かない。** 1 行の要約と Issue へのリンクだけにする。

## Issue の書き方

テンプレート（不具合／やりたいこと）に沿って書く。

- **背景・やること・完了の条件**を必ず書く。完了の条件は、確かめ方まで含める。
  Issue だけ読めば着手できるように書く（AI に「#12 をやって」と頼めるように）。
- 仕様が決まっていないものは `idea` ラベルを付け、「やること」に**未定**と書く。着手時に仕様から決める。
- 関係する仕様・設計・ADR・Issue をリンクする。

## ラベル

種類はコミット・PR と同じ語彙（[branch-and-pr.md](branch-and-pr.md)）。

| ラベル                                                                            | 使うとき                             |
| --------------------------------------------------------------------------------- | ------------------------------------ |
| `feat` / `fix` / `perf` / `refactor` / `test` / `docs` / `build` / `ci` / `chore` | 作業の種類                           |
| `idea`                                                                            | まだ検討段階（仕様が決まっていない） |
| `dependencies` / `github_actions`                                                 | Dependabot が付ける                  |

## PR との結び付け

PR の本文に `Closes #12` と書くと、マージで Issue が閉じる。1 つの PR で複数閉じるなら `Closes #12, closes #13`。
Issue の一部だけ済ませる PR は `Refs #12` にして、Issue は閉じない。

## Project（やる順番）

[Project「Pathly」](https://github.com/users/y-nosuke/projects/3) に Issue を入れ、**やる順番は並び順で表す**（上から着手する）。
優先度や期日などの項目は足さない。roadmap には順番を書かない（二重管理にしない）。

| ビュー         | 中身                                                         |
| -------------- | ------------------------------------------------------------ |
| ボード         | Status（Todo／In Progress／Done）の列。全体を見渡す          |
| 着手できるもの | 開いていて `idea` でないもの（仕様が決まっていて始められる） |

- 着手したら In Progress に移す。Issue が閉じる（PR のマージで `Closes`）と Done に移る（Project の自動化）。
- 新しい Issue は Project の自動化（Auto-add）で自動で入る。並び順は手で整える。
- AI に頼むときは「Project の『着手できるもの』のいちばん上をやって」のように指せる。
