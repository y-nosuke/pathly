# Issue を並行して進める

複数の Issue を、Claude の別々のセッションに並行して実装してもらうときの決まり。
手順の正は [start-issue](../../.claude/skills/start-issue/SKILL.md)・[emulator-check](../../.claude/skills/emulator-check/SKILL.md)・
[phone-check](../../.claude/skills/phone-check/SKILL.md) のスキル。ここには「なぜそうするか」と並べ方の決まりを書く。

---

## 考え方: 実装は並行、確認は 1 つずつ

エミュレータは 1 台、スマホに入る開発版（`com.pathly.debug`）は 1 つ、確かめる人も 1 人。
台数を増やすより、**実装（コードの編集・コンパイル・ユニットテスト）だけを並行にし、確認は順番に回す**。

| 段                                               | 並行にできるか | 仕組み                                                                       |
| ------------------------------------------------ | -------------- | ---------------------------------------------------------------------------- |
| 実装・コンパイル・ユニットテスト（1 パッケージ） | できる         | セッションごとに **worktree**（別のフォルダ・別のブランチ）                  |
| `./gradlew build`・instrumented test             | 1 つずつ       | `run-build.sh`・`run-instrumented.sh` が worktree をまたいで**順番待ち**する |
| エミュレータで画面を触る                         | 1 つずつ       | `hold-check-lock.sh` で同じ順番待ちに並ぶ                                    |
| スマホで確かめてもらう                           | 1 つずつ       | 確認待ちの列（ユーザーに 1 つずつ確かめてもらう）                            |
| コードの確認・push の承認                        | 1 つずつ       | ユーザー                                                                     |

順番待ちを入れたのは、エミュレータが 1 台しかないことに加えて、次のためでもある。

- instrumented test は開発版を入れ直し、終わると消す。別のセッションが画面を触っている最中に走ると、その画面が消える。
- ビルドが止まったときの後始末（`./gradlew --stop`）は、この PC の gradle のデーモンを**すべて**止める。
  重いビルドが並んでいると、関係ない方も落ちる。2 つ並べると PC も重くなる。

## 並べ方の決まり

- **同時に進めるのは 2 本まで**から始める。確認（コード・スマホ）が溜まるので、増やすのは詰まり具合を見てから。
- **DB のスキーマを変える Issue は同時に 1 つだけ**。端末の DB は入れ替えのたびにまっさらにする（下）ので困らないが、
  コードでは 2 つのブランチが同じ版の `MIGRATION_N_N+1` と `schemas/N+1.json` を作ってしまう。後からマージする方で版を
  付け直してマイグレーションと schema を作り直すことになり、「version を上げる前にコンパイルしない」の落とし穴もある。
- 並べる Issue は**触る画面・層が離れたもの**を選ぶ。`strings.xml`・ナビゲーション・`README.md` の機能一覧・docs は
  どの Issue でも触りがちで、衝突しやすい。
- **後からマージする側は、main を取り込み直してから**確かめる（build・instrumented test・スマホ）。
- Project の In Progress は複数になってよい。

## worktree

- Claude Desktop のセッションを worktree で始める（または `EnterWorktree`）。worktree は `.claude/worktrees/` に作られる
  （`.git/info/exclude` で git の対象外）。
- 始めたら **`.claude/skills/start-issue/setup-worktree.sh`** を 1 回。git に入らない `android/local.properties`
  （Google Maps のキー）を本体からコピーする。無いとビルドは通るが、開発版の地図が出ない。
- main は本体で checkout されているので、worktree では `git checkout main` できない。ブランチは `origin/main` から切る
  （[start-issue](../../.claude/skills/start-issue/SKILL.md) の 4）。
- gradle のビルド結果（`android/build`・`android/app/build`）は worktree ごとに別。最初のビルドは時間がかかる。

## 開発版の入れ替え（スマホ・エミュレータ）

ブランチごとに DB の版や形が違う。別のブランチの開発版を上書きで入れると、DB の版を下げられずに落ちたり、
同じ版で形が違って落ちたりする。versionCode もコミット数なので、コミットの少ないブランチの開発版は上書きでは入らない。

- **入っている開発版のコミットが、今のブランチの祖先のときだけ上書きで入れる**（同じブランチの前のコミット、
  または分岐元の main）。DB の版は一本道で上がるだけなので、マイグレーションで移せる。
- **それ以外（別のブランチ・見分けられない）は、アンインストールしてまっさらな状態から入れる**。
  データは**リリース版から書き出したファイルを読み込んで**使う（古い版の書き出しは、読み込んだあとに今の形へ移し替えられる。
  [specs/backup.md](../specs/backup.md)）。読み込むたびに、リリース版の版からのマイグレーションを実データで確かめることにもなる。
- アンインストールで開発版のデータは消える。残したいものがあれば、先に開発版から書き出してもらう。
- 入っている開発版のコミットは、版名（`0.5.0+dev.3.abc1234` の `abc1234`）で分かる。見方は
  [phone-check](../../.claude/skills/phone-check/SKILL.md) の 2。

## 採らなかった案（今は）

- **ブランチごとに `applicationIdSuffix` を変え、開発版を並べて入れる**: Google Maps の API キーをパッケージ名で
  制限していれば足す必要があり、データもアプリごとに別になって準備の手間が増える。確かめる人が 1 人なので、
  並べても確認は速くならない。
- **エミュレータを 2 台立てる**: メモリを食い、スクリプト（`emulator-5554` 決め打ち・固まったときに名前で止める）も
  作り直しが要る。ビルドと instrumented test を合わせても 1 周 7 分ほどで、順番待ちで足りる。

順番待ちが辛くなったら、別の Issue で考え直す。
