# 0022. GPS が取れなかった区間は、線では繋がず距離では直線で補う

- Status: Accepted
- Date: 2026-08-18

関連: 補正（平滑化）の設計は [../designs/smoothing.md](../designs/smoothing.md)。
記録の仕様は [../specs/recording.md](../specs/recording.md)。

## Context（背景）

新幹線で移動しながら記録すると、地図の線が長い直線で飛ぶ。原因は 3 つある。

1. **トンネル**。山陽新幹線は路線の大半がトンネルで、六甲トンネルだけで 16km ある。
   衛星が見えないので取れる位置が無い。
2. **車体による遮蔽**。金属の車体とコーティングされた窓で、屋外より信号が弱い。
3. **アプリが止まっている間**。更新・強制終了のあと、ユーザーがアプリを開くまで
   サービスは復帰しない（OS がアプリを停止状態に置くため）。実際に、アプリが復帰するまでの
   間に 160km の空白ができた。

1 と 2 は物理的な話でアプリ側では塞げない。問題はその**扱い**だった。点は時刻順に
1 本の線として繋いでいたので、空白の前後がそのまま結ばれ、

- 地図に**通っていない直線**が、実測の軌跡とまったく同じ見た目で描かれる
- 平滑化の窓（5 点）が空白をまたいで平均し、境目の点が引き寄せられる

欠落と実測の区別が付かない状態になっていた。

一方で**距離は別の話**だった。当初これも「空白ぶんが乗るのは水増し」と考えて除いたが、
これは誤りだった。**2 点間の実際の移動距離は、その 2 点を結ぶ最短距離を必ず上回る。**
したがって空白の直線距離を足しても真の距離を超えることはなく、足すほど下から近づく。
除くと、実際よりはるかに短い数字（上の例では 160km ぶん）が出てしまう。

## Decision（決定）

**大きく時間が空いた前後は、繋がっていないものとして扱う。**

- `TrackSegments.split` が点列を「途切れていない区間」に分ける。しきい値は **3 分**
  （`GAP_MILLIS`）。設定できる最長の記録間隔が 60 秒なので、その 3 倍。
- **地図は区間ごとに線を引く**（実線ではまたいで結ばない）。空白は**灰色の破線**で結び、
  前後の位置関係が分かるようにする。**色と模様の両方**で軌跡（オレンジの実線）と分ける。
  模様だけでは足りないのは、模様の長さが画面のピクセル基準だから。縮尺を小さくすると
  区間が数十ピクセルまで縮み、破片が 1〜2 個しか描けず実線と見分けが付かなくなる。
  太さは軌跡と同じにする（薄く細くすると地図に埋もれて見つけられない）。
- **距離は空白の直線距離を足した値**を使う（補完したぶんは下限なので過大にならない）。内訳は
  `measuredDistanceMeters`（記録できた分）と `bridgedDistanceMeters`（補完した分）に分けて持ち、
  経路詳細で「記録が途切れた区間が N 箇所（距離のうち M km は直線で補完）」と見せる。
  同じ場所で再開したときは補完ぶんが 0 になるので、**箇所数を主語にして**「0.0km」を出さない。
- **平滑化も区間ごと**に行う（`TrackSmoother.smoothSegments`）。窓が欠落をまたがない。
- **立ち寄りの検出もまたがない**（`StopDetector` が区間ごとに判定する）。滞在時間は点と点の
  時刻の差で測るので、またぐと「取れていなかった時間」まで滞在に数えてしまう。アプリが
  止まっている間に出掛けて同じ場所に戻ると、その往復がまるごと 1 回の長い滞在になる。
- **灰色は欠落専用にする。**調整モード（デバッグビルド）で重ねる生データは灰色だったが、
  意味の違う線が同じ色になるので紫にした。

GPX が `<trkseg>`（トラックセグメント）で同じことを表現しているのと同じ考え方で、
1 本のトラックの中に「連続した区間」が複数ある、という形にする。

### 保存済みの補正点は作り直す

`smoothed_points` は**末尾に足すだけ**で既存の行を書き直さない（記録中の差分INSERT）。
そのため上の決定を入れただけでは、**すでに記録した経路は直らない**。欠落の向こう側と平均された
座標を持ったままで、窓が5点なら欠落直前の点は向こう側へ 2/5 だけ引き寄せられている
（160km の空白なら 64km）。放っておくと、その架空の移動が**実測の実線**として地図に描かれ、
距離の内訳でも「記録できた分」に数えられる。**この ADR が直したかった記録そのものが直らない。**

- `TrackSmoother.GENERATION`（平滑化の世代）を持ち、保存済みの点がどの世代で作られたかを
  `MaintenanceStore`（SharedPreferences）に覚えておく。古ければ起動時に
  `resmoothGappedTracks()` が**欠落を含む完了済み経路だけ**を作り直し、距離も焼き直す。
- **やり切れたときだけ世代を進める。**途中で落ちても、記録中の経路があって触れなくても、
  次の起動でやり直される（作り直しは何度やっても同じ結果なので、繰り返して困らない）。
- **差し替えは経路ごとに原子的**にする（`SmoothedPointDao.replaceForTrack`）。消してから
  入れ直す形だと、その間にプロセスが死んだとき **0 行のまま残る**。すると次の起動では
  「欠落なし」と見えて対象から外れ、**二度と直らない**（地図はその場の計算で正しく出るので
  気づきにくいが、焼き込んだ距離は古い値のまま固定される）。組み立ててから丸ごと入れ替える。
- **立ち寄りは検出し直さない。**手で足した・付け替えた・メモを書いたものを壊すため。
  やり直したいときはユーザーが再解析から行う（→ [0012](0012-non-destructive-reanalysis.md)）。

## Alternatives（検討した没案）

- **マップマッチングで線路・道路に吸着させる**（Google Roads API / OSM 系）… 空白が
  もっともらしい線になり距離も現実的になる。Google マップのタイムラインがやっていること。
  だが**実測ではなく推測**で、それを実測と同じ見た目で混ぜると区別が付かなくなる。
  API 課金も乗り、オフラインで完結する今の性格からも外れる → 却下。
  自分で「ここは新幹線だった」と注記する形（手動・非破壊）なら将来あり得る。
- **センサーで補う（デッドレコニング）** … カーナビは車速パルスとジャイロで成立するが、
  端末は車両に対して静止しているので加速度計からは「動いていない」ようにしか見えない。
  新幹線では原理的に効かない → 却下。
- **しきい値を記録間隔に連動させる**（間隔 × N）… 設定を変えると過去の経路の見え方が変わる。
  間隔は記録ごとに違い得るのに、持っているのは「今の設定」だけ → 却下。最長間隔から決め打つ。
- **空白に何も描かない** … 誤解の余地は最も小さいが、離れた 2 つの区間が同じ経路のものだと
  分かりにくく、地図上で目が迷子になる。点線＋薄い色で実線と十分に区別できるので、
  **位置関係が分かる方を採った**。
- **距離からも空白を除く** … 「記録できた距離」としては正確だが、欠落が長いと実際より
  はるかに短い数字になる。直線距離は下限値で過大にならないので、**足す方が実際に近い** → 却下。
- **作り直しの目印を DB に持つ**（`gps_tracks` に平滑化の世代の列を足す）… 経路ごとに
  進み具合が残るので中断に強い。だが 1 回きりの修復のためにマイグレーションを 1 つ増やす。
  作り直しは何度やっても同じ結果で、失敗したら丸ごとやり直せばよいので、
  端末に 1 つの数字（SharedPreferences）で足りる → 却下。
- **全経路を無条件に作り直す** … 判定が要らず単純。だが欠落の無い経路まで全点を読み直す。
  平滑化は時刻を動かさないので、**保存済みの点列を見れば欠落があったかは分かる** → 却下、
  欠落を含む経路だけにする。
- **速度 × 空白の時間で見積もる** … 直前の速度から推測する。今回の例に新幹線の巡航速度を
  当てはめて計算しても、直線距離を下回る見積もりにしかならなかった。空白の間に停車や加減速が
  あれば平均速度は落ち、逆に速く見積もれば真の距離を超えかねない。**どちら側に外れるか
  分からない**のが難点 → 却下。直線距離は必ず下回る側に外れるので、下限としてはこちらが確実。

## Consequences（結果・トレードオフ）

- 地図で**欠落が欠落として見える**（点線）。距離は下から近い値になる。
- **点線は「そこを通った証拠」ではない**。前後の点を最短で結んだだけで、実際の経路は分からない。
- 補完したぶんは**実際より短く出ることはあっても、長く出ることはない**。迂回していたぶんは
  拾えない。ただし**総距離が必ず実際を下回るとは言えない**：記録できた区間ぶんは GPS ノイズで
  上振れし得る（平滑化はそれを減らすだけで消さない）。下限だと言えるのは補完したぶんだけ。
- 短い欠落（3 分未満）は今までどおり実線で結ぶ。短いトンネルはほぼ直線なので実態に近い。
- 距離の合計は以前とほぼ変わらない（空白を直線で足す点は同じ）。変わったのは
  **内訳を持ったこと**と、**地図で実測と補完を区別するようになったこと**。ただし作り直した
  経路では、欠落の周りの点が本来の位置に戻るぶん、実測と補完の**内訳が大きく変わる**。
- 平滑化を変えて既存データを作り直したくなったら、`TrackSmoother.GENERATION` を上げる。
  これまで「一度補正した軌跡をやり直す手段は無い」としてきたが、**アプリ側の都合で作り直す道**
  ができた（ユーザー操作としては引き続き無い）。
- より実際に近づけたいなら、空白の両端を道路・線路の網に載せて経路探索する
  （マップマッチング）方向になる。課金とオンライン前提、移動手段の指定が要るので、
  やるなら別の機能として立てる。
