# 0012. 再解析・再補正は破壊的にやり直さず、追加提案（非破壊・opt-in）にする

- Status: Accepted
- Date: 2026-08-01（記録は 2026-08-15 に遡って作成）

関連: 記録中の増分検出と境界の扱いは [0002](0002-incremental-live-stop-detection.md)。

## Context（背景）

かつて経路詳細には、やり直し系のボタンが 2 つあった。

- **軌跡を再補正** … その経路の `smoothed_points` を全消去し、生の `gps_points` から計算し直す。
- **再解析** … その経路の `stops` を全消去し、検出し直して作り直す。

どちらも「作り直せば正しくなる」という発想だったが、**ユーザーが手を加えた結果を消してしまう**。
とくに再解析の害が大きかった。誤検知として**手で削除した立ち寄りが、押すたびに復活する**のである。
生データには滞在の痕跡が残っているのだから、検出し直せば当然また出てくる。削除という操作が
「消したい」という意思表示なのに、それを保存する場所がどこにも無かった。

命名・メモ・名前の付け替えといったキュレーションも、作り直しで一緒に失われた。

## Decision（決定）

**やり直し系の操作は、既存のデータに触れない「追加提案」にする。**

- 再解析は `detectMissingStops` で検出し直し、**既存の立ち寄りと時間帯が重ならない候補だけ**を挙げる。
  永続化はしない。ユーザーが**チェックした分だけ**を `addStops` で追加する。
- 既存の `stops` は消さない・変えない。
- **再補正（`recomputeSmoothed`）と再検出（`redetectStops`）は撤去する**。補正のやり直しは提供しない。

「復活させるかどうか」を 1 件ずつユーザーが決められる形にする、というのが要点。
削除した誤検知はチェックしなければ復活せず、削除した本物はチェックすれば戻せる。

## Alternatives（検討した没案）

- **削除した立ち寄りを「却下リスト」に覚えさせ、破壊的な再解析を続ける** … 復活は防げるが、
  却下を貯めるテーブルと、その掃除の面倒を抱える。しかも命名・メモの喪失は解決しない → 却下。
- **再解析を確認ダイアログ付きにする** … 「本当に作り直しますか」を出すだけでは、失うものが
  ユーザーに見えていない（何件のキュレーションが消えるか分からない）→ 却下。
- **再補正は残す**（補正は人が手を加えないので破壊的でも無害という理屈）… 補正点列は立ち寄り検出の
  入力なので、作り直すと検出結果が動き、結局 stops に波及する。パラメータ調整は開発時の
  デバッグ機能（`tuningMode`）で足りる → 却下。

## Consequences（結果・トレードオフ）

- ユーザーの操作結果（削除・命名・メモ）が、どのボタンを押しても失われなくなった。
- **しきい値を厳しくしても、既存の stop は消えない**。「もう立ち寄りでない」ものは手で削除する。
- **却下した候補は記憶しない**ので、再解析のたび同じ候補が再掲される。チェックしなければ無害なので
  当面は放置し、煩わしくなったら「却下の記憶」を足す。
- 補正パラメータを変えても保存済みの補正点列には反映されない（やり直す手段が無い）。
  これは意図した割り切りで、必要になったら開発ビルドで確認する。
- 判断用に候補へ場所名を添えるため、**再解析を押すと候補ぶんの Places 呼び出しが発生しうる**
  （近くの命名済み place を再利用して無料化、追加時は焼き込んで二度叩かない）。
  命名の「place 1 件 1 回」原則（[0014](0014-place-naming-cost-policy.md)）の外側にある点は留意する。
