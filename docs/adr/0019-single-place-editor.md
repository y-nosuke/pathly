# 0019. 登録済みの場所の編集画面を1つに統一する（入口だけを変える）

- Status: Accepted
- Date: 2026-08-16

関連: [ADR-0009](0009-map-tap-behavior.md) の「登録済みマーカー＝その場所の詳細を開く」を置き換える。
確定版の表は [../specs/map.md](../specs/map.md)、置き場は [../designs/ui.md](../designs/ui.md)。

## Context（背景）

登録済みの場所を開く入口が 2 つある。

- **場所タブの一覧から行を選ぶ** → 場所詳細（`PlaceDetailContent`）
- **地図のマーカーをタップする**（記録画面・経路詳細・場所詳細の地図） → 場所シート（`PlaceActionSheet`）

同じ「登録済みの場所」を開いているのに、できることが違っていた。シートには **Google 施設の紐付け・
訪問履歴・削除が無く**、訪問回数の表示も欠け、保存ボタンの活性制御も無い。もともとシートは
「地図を見ながらの軽い編集」のつもりで、重い操作は「詳細を開く」の先に置く切り分けだった。

実際に使ってみると、この切り分けが**混乱の原因**になった。どちらの入口から開いたかを覚えていないと
何ができるか分からず、「さっきは消せたのに」と探すことになる。地図から場所を消したいのに、
一度詳細へ移動しないと消せないのも遠回りだった。

## Decision（決定）

**登録済みの場所の編集は、入口が違っても同じものを出す。**

- 編集部を `presentation/places/PlaceEditorBody` 1 つに集約し、場所詳細と場所シートの両方がこれを呼ぶ。
  器（地図・カメラ・戻る・シートの開閉）だけが画面ごとに違う。
- したがって**地図からも削除できる**。削除は場所一覧と同じ流儀（確認ダイアログを出さず即時、
  スナックバーの「取り消す」で戻す）に揃え、通知の型と表示を `PlaceDeleteUndo` に共通化する。
  記録画面にはスナックバーが無かったので新たに置く。
- 入口が同じものを出すので、シートの「詳細を開く」は**廃止**する。同じ画面へ移動するだけのボタンになり、
  「何かが増えるはず」と思わせてしまうため。
- 単一 place は `WishlistRepository.observePlace` で**購読**する。保存しても値が古くならず、
  削除されたらシートが自分で閉じられる（以前は一回読みのスナップショットで、保存＝即閉じだった）。

## Alternatives（検討した没案）

- **表示のズレ（訪問回数・保存の活性・ラベル・ヒント）だけ直す** … 一番安いが、Google 紐付け・
  訪問履歴・削除の差が残るので「入口で違う」という混乱そのものは消えない → 却下。
- **表示＋Google 紐付けまで揃え、履歴と削除は詳細に残す** … 削除の取り消しは「場所一覧へ戻る」導線と
  セットで成立していたので、地図から消せるようにするならスナックバー基盤を増やす必要があり、
  そこを避けるための線引きだった。しかし利用者にとっては「消せる場所と消せない場所がある」だけで、
  理由は見えない → 却下。
- **「詳細を開く」を残す** … 中身が同じなら移動する意味が無く、押した先で何も増えないのは
  かえって分かりにくい → 却下（地図をその場所中心に見たいという用途は残るが、一覧から開けば済む）。
- **シートを廃止して常に場所詳細へ遷移させる** … 記録中に地図を離れることになり、
  「地図を見ながら直す」という場所シートの利点（[ADR-0010](0010-non-modal-map-sheets.md)）を失う → 却下。

## Consequences（結果・トレードオフ）

- 入口を覚えなくてよくなる。片方にだけ機能を足す事故も、実体が 1 つなので起きにくい。
- 記録画面・経路詳細の ViewModel が、場所タブと同じ機能（訪問履歴・削除・取り消し・名前検索）を
  持つことになった。`PlacesTextSearcher` を両方に注入している。
- **シートが縦に長くなる**（訪問履歴・削除まで載る）。畳める非モーダルシートなので破綻はしないが、
  地図を見ながらの軽い操作としては情報量が増えた。使ってみて重いようなら、履歴を折りたたむなどの
  調整余地がある。
- 場所シートの訪問履歴から経路詳細へ飛べるので、**経路詳細から経路詳細へ**入れ子で入れる。
  バックで戻れるので実害は無いが、深くは辿れる。
- `observePlace` は一覧の Flow から絞る実装なので、場所が非常に多い環境では 1 件の購読でも
  全件の変換が走る。現状の規模では問題にならないが、増えたら専用クエリに替える。
