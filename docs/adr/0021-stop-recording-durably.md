# 0021. 記録の停止は確定より先にトラックを閉じ、停止後は自己回復させない

- Status: Accepted
- Date: 2026-08-18

関連: 異常終了からの自己回復（START_STICKY）と中断記録の扱いは
[../specs/recording.md](../specs/recording.md)。確定処理の中身は
[../designs/smoothing.md](../designs/smoothing.md) / [../designs/stops.md](../designs/stops.md)。

## Context（背景）

「記録を終了したのに、アプリを開き直すと記録中に戻っている」。

停止の処理はこうなっていた。

1. `isTracking = false`／位置更新の解除
2. `Command.Finish` をキューの最後尾に積む
3. 確定（全点の再平滑化・立ち寄り検出）→ **そのあと** `finishTrack`（`isActive = 0`）
4. 確定が終わってから `stopSelf()`

確定を先に済ませてから閉じていたのは、**停止時点で滞在中だった立ち寄りを取りこぼさない**ため。
これ自体は正しい配慮だったが、3 の確定は経路が長いほど時間がかかる（数百点の再平滑化と
立ち寄り検出をやり直す）。**その間にプロセスが死ぬと、アクティブなままの経路が残る。**

そして `onStartCommand` は停止のときも `START_STICKY` を返していた。停止を受けたあと
`stopSelf()` に到達する前にプロセスが死ぬと、OS がサービスを null intent で作り直し、
`restoreTrackingIfNeeded()` が「アクティブなトラックがある＝続きを記録する」と判断する。

結果、**止めたはずの記録が復活し、通知も出ないまま裏で記録が続く**。次にアプリを開くと
記録中に見える。アプリをタスクから消す・OEM の電池管理に落とされるといった、日常的に起きる
操作で踏む。

## Decision（決定）

**止めた事実を、時間のかかる処理より先に永続化する。**

- `Command.Finish` は `finishTrack`（`isActive = 0`）を**先に**行い、確定はそのあとに続ける。
  終了時刻も「確定が終わった時刻」より「止めた時刻」の方が実態に合う。
- `ACTION_STOP_TRACKING` を受けた `onStartCommand` は **`START_NOT_STICKY`** を返す。
  最後の戻り値が採用されるので、停止後に OS がサービスを作り直すことがなくなる。
  記録中の異常終了からの自己回復（`START_STICKY`）はそのまま残す。

## Alternatives（検討した没案）

- **確定が終わるまで停止ボタンを押させない（進捗を出して待たせる）** … 取りこぼしも復活も防げるが、
  長い経路で数秒〜数十秒待たせることになる。停止は「もう終わり」という操作なので待たせたくない → 却下。
- **`restoreTrackingIfNeeded()` に時間制限を入れる**（最終点から N 分以上経った経路は再開しない）…
  復活は減らせるが、閾値の根拠が無く、長い休憩を挟んだ記録を勝手に打ち切る恐れがある。
  そもそも「止めた」という事実を持たずに推測しているのが問題 → 却下。
- **停止したことを SharedPreferences に持ち、再起動時に見る** … DB の `isActive` と同じことを
  二重に持つことになる。状態の置き場が増えるほど食い違う → 却下。`isActive` を正にする。
- **`onTaskRemoved` でサービスを畳む** … タスクを消した瞬間は塞げるが、OS や電池管理による
  プロセス終了は塞げない。根本ではない → 却下（将来足すとしても、この決定とは別の話）。

## Consequences（結果・トレードオフ）

- **止めた記録が復活しなくなる。** これが主目的。
- **確定の途中でプロセスが死ぬと、末尾の平滑化・立ち寄り検出が不完全なまま残る。**
  これは今回受け入れたトレードオフ。ただし総移動距離は起動時のバックフィル
  （`isActive = 0 AND totalDistanceMeters IS NULL`）が拾い、取りこぼした立ち寄りは
  **再解析**（→ [ADR-0012](0012-non-destructive-reanalysis.md)）で足せる。
  裏で記録が走り続けるより害が小さい、という判断。
- 通常の停止では確定はそのまま続けて走るので、**取りこぼしは起きない**。塞いだのは
  「停止直後にプロセスが死ぬ」という異常時だけ。
- 停止直後にプロセスが死んだ場合、経路は閉じた状態で残る。中断ダイアログは出ない
  （出す必要が無い＝ユーザーは実際に止めているため）。
