# 0021. 記録の停止は確定を待たせて見せ、停止後は自己回復させない

- Status: Accepted
- Date: 2026-08-18

関連: 異常終了からの自己回復（START_STICKY）と中断記録の扱いは
[../specs/recording.md](../specs/recording.md)。確定処理の中身は
[../designs/smoothing.md](../designs/smoothing.md) / [../designs/stops.md](../designs/stops.md)。
取りこぼした立ち寄りを後から足す手段は [0012](0012-non-destructive-reanalysis.md)。

## Context（背景）

「記録を終了したのに、アプリを開き直すと記録中に戻っている」。長い記録でだけ起きる。

停止の処理はこうなっている。

1. `isTracking = false` ／ 位置更新の解除
2. `Command.Finish` をキューの最後尾に積む
3. **確定**（全点の再平滑化・立ち寄り検出）→ そのあと `finishTrack`（`isActive = 0`）
4. 確定が終わってから `stopSelf()`

3 の確定にかかる時間は**点数にほぼ比例する**。短い記録なら一瞬だが、数時間・数百点だと数秒かかる。
その間ずっと「アクティブなままの経路」が DB に残り、画面上は既に停止済みに見える。

そして `onStartCommand` は停止のときも `START_STICKY` を返していた。`stopSelf()` に到達する前に
プロセスが死ぬと、OS がサービスを null intent で作り直し、`restoreTrackingIfNeeded()` が
「アクティブなトラックがある＝続きを記録する」と判断する。**止めたはずの記録が復活し、裏で
記録が続く。** 長い記録でだけ起きるのは、窓が開いている時間が長いから。

## Decision（決定）

**確定を待たせて、待っていることを見せる。そして停止後は OS に作り直させない。**

- `Command.Finish` は**確定 → `finishTrack` の順を守る**。逆にすると、確定が途中で終わった経路が
  「きれいに終わった経路」として履歴に並び、末尾の立ち寄りが欠けていることに気づけない。
  確定が終わらなければ `isActive = 1` のまま残り、次の起動で「再開する／完了にする」として
  現れる＝**失敗が隠れない**。
- 停止から確定完了までを `LocationTrackingService.isFinalizing` として公開し、画面は
  **ローディングで覆ってバックを塞ぐ**。通知の文言も「記録を保存しています...」に変える
  （画面を離れていても終わっていないことが分かる）。
- `ACTION_STOP_TRACKING` を受けた `onStartCommand` は **`START_NOT_STICKY`** を返す。
  最後の戻り値が採用されるので、停止後に OS がサービスを作り直さない。記録中の異常終了からの
  自己回復（`START_STICKY`）はそのまま残す。
- 中断された記録を「完了にする」ときも**同じ確定を通してから閉じる**。素通しで閉じると、
  確定できずに中断した経路が確定済みの顔で履歴に並ぶ。

## Alternatives（検討した没案）

- **確定より先に `finishTrack` して、止めた事実を真っ先に永続化する** … 復活は確実に止まるし
  待たせもしない。しかし確定が途中で終わった経路が**確定済みの顔で残る**ため、
  「保存できていないのに終わったように見える」状態を作ってしまう。今回避けたかったのは
  まさにそこなので却下（一度この形で実装してから戻した）。
- **`restoreTrackingIfNeeded()` に時間制限を入れる**（最終点から N 分以上経った経路は再開しない）…
  復活は減らせるが閾値の根拠が無く、長い休憩を挟んだ記録を勝手に打ち切る恐れがある。
  そもそも「止めた」という事実を持たずに推測しているのが問題 → 却下。
- **停止したことを SharedPreferences に持つ** … `isActive` と同じことを二重に持つことになり、
  食い違うと厄介 → 却下。`isActive` を正にする。
- **`onTaskRemoved` でサービスを畳む** … タスクを消した瞬間は塞げるが、OS や電池管理による
  プロセス終了は塞げない。根本ではない → 却下。

## Consequences（結果・トレードオフ）

- **止めた記録が復活しなくなる。** これが主目的。
- 停止のあと**確定が終わるまで待たされる**。長い記録ほど待ち時間が伸びる。何が起きているかは
  ローディングと通知で見せるので、固まったようには見えない。
- **バックで塞げるのはバックだけ。** タスクから消す・OS に落とされるのは防げない。その場合は
  経路が `isActive = 1` のまま残り、次の起動で「再開する／完了にする」を選ぶことになる。
  勝手に記録が復活するよりは、選ばせる方がよいという判断。
- ここで保証しているのは**中断（プロセスの死・キャンセル）が隠れないこと**。確定の内部で
  起きた例外は従来どおりログに出して握りつぶすので、そちらは経路が閉じたまま残る。
  取りこぼした立ち寄りは再解析（→ [0012](0012-non-destructive-reanalysis.md)）で足せる。
