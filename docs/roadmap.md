実装するときに改めて仕様を検討する。設計書には置かない。

### 立ち寄り検出の精度を上げる

いまの検出は**位置と時間だけ**なので、信号待ち・渋滞・GPSドリフト・屋内での座標の固まりを
誤検知する。Google Maps や iOS の訪問検出が精度良いのは、**位置以外の信号**で「本当に止まったか」を
判定するため。効く順に:

1. **アクティビティ認識**（最優先）… Android の Activity Recognition API で「静止／徒歩／自転車／車」を
   判定し、**車で停車中などは滞在にしない**。信号待ち系の誤検知が大きく減る。`ACTIVITY_RECOGNITION` 権限が要る。
2. **精度フィルタ／重み付け** … accuracy の悪い点を除外・軽く扱い、静止中のドリフトを抑える。
3. **到着／出発のヒステリシス** … 入る判定と出る判定で別しきい値にして境界のバタつきを防ぐ。
4. **Wi-Fi / Bluetooth / セル基地局** … 同じ AP・セルに繋がり続けている＝静止、の補助（屋内で強い）。
5. **POI スナップ** … 既知施設の輪郭に吸着（立ち寄り版のマップマッチング）。
6. **機械学習** … ラベル付きデータで学習したモデル。

まずは 1 だけでも体感がかなり変わる見込み。

### 軌跡の補正を強くする

補正の「はしご」（下ほど強力・重い）。いまは 1〜2 段目（ジャンプ除外＋精度重み付き平滑化）まで。

- **カルマンフィルタ** … 位置＋速度を状態として予測→観測で補正する定番の後段処理。
  **記録中（リアルタイム）と相性が良く**、未来の点が要らないので平滑化のラグが原理的に出ない。
  いまの重み付き平均を置き換える候補。非線形には Extended / Unscented KF。
- **マップマッチング** … 軌跡を道路ネットワークに吸着させる。「経路をきれいに」する効果は最大。
  OpenStreetMap のデータ＋ OSS エンジン（OSRM の `match` / Valhalla の Meili / GraphHopper など）で
  実現できる。地図データか外部 API が要り、重い・コスト増。見た目の劇的改善が欲しくなった段階で検討。
- より頑健な**スパイク検出** … 「速いが継続（乗り物）／1点だけ飛んで戻る（グリッチ）」を区別する。

### クラウド同期（Phase 3 の土台）

Supabase（PostgreSQL）側は**まだ設計していない**。決めることの一覧:

- テーブル（users / tracks / gps_points / user_relationships）と、Room との対応
- 主キーを UUID にするか（同期時の競合を避けるため）
- 競合解決（タイムスタンプの最終更新優先＋手動選択）
- RLS ポリシー・認証認可・クラウド側の暗号化
- Edge Functions・リアルタイム同期・オフライン対応
- 端末側も暗号化するか（いまは平文）

方針だけは決まっている: **オフライン優先**（Room をメインに置き、接続時に同期する）。
