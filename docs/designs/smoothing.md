# GPS軌跡の補正（スムージング）設計

## 概要

GPSの生データはノイズで「経路がぐちゃぐちゃ」になり、距離も実際より膨らむ。これを補正して、表示される軌跡と移動距離を実際に近づける。

> 対応する要望: [requirements.md](../requirements.md) の「記録した経路をきれいに見たい／正確な距離を知りたい」。ロードマップ Phase 2「GPSノイズ除去（位置補正）」。
> 用語の日英対応（生データ・補正後の点列・補正・平滑化など）は [glossary.md](../specs/glossary.md) を参照。
> データモデル（`smoothed_points` 等）は [../specs/model.md](../specs/model.md) を参照。

## 設計方針

### 1. 非破壊 ＋ 補正後を保存（記録中に計算）

原データ（`gps_points`）は一切変更しない。補正後の点列は**別テーブル `smoothed_points` に保存**する。補正の計算は**記録中に増分で行い**、確定した点から順に保存する（従来の「読むたびに毎回計算」からの変更。詳細は後述「記録中の補正と保存」）。

- **記録中にライブ表示できる**: 補正後の軌跡・距離をその場で描ける。
- **一覧が軽い**: 表示のたびに全点を再計算しない。
- **削除しない方針に合致**: 生データは無改変。補正はあくまで別データとして併存させる（位置情報は個人に委ね自動改変しない、というプロジェクト方針と揃う）。
- **原データが残る**: 生点はそのままなので、将来アルゴリズムを変えたくなっても計算し直せる素材は失わない
  （ただし**やり直す導線はアプリに持たない** → [ADR-0012](../adr/0012-non-destructive-reanalysis.md)）。

トレードオフ: 記録中に端末で計算するぶん電池・CPUを多少使う。DBへは**確定した点だけを書き込む増分保存**にして負荷を抑える（平滑化の計算自体はトラック全体を対象に再計算するが、GPS間隔＝10秒以上では無視できる）。また補正後を保存するぶんスキーマ変更（Room v2→v3）が要る。

### 2. accuracy を「足切り」ではなく「重み」に

各GPS点には精度 `accuracy`（メートル）が付く。これを**ハードなしきい値**で切るのではなく、**重み**として使う。精度が悪い点ほど軽く扱うことで、マジックナンバー（精度上限・最小移動など）を減らし、「感覚で決める」要素を小さくする。

## アルゴリズム

`TrackSmoother.smooth(points, params)`（`domain/model/TrackSmoother.kt`）。2段階。

### Step 1: ジャンプ除外

直前の採用点との速度が `maxSpeedMps` を超える点を、明らかな外れ値として除外する。

```text
速度 = 直前点との距離(m) / 経過秒
速度 > maxSpeedMps → その点を捨てる
```

しきい値は**乗り物を通し、GPSグリッチだけ落とす**高さにする。低すぎる（例: 55 m/s ≒ 200km/h）と新幹線（約83 m/s）が丸ごと除外され、混在トラック（徒歩→新幹線→徒歩）で中間区間が欠落し距離を過小評価する。既定は **150 m/s（≒540km/h）**：新幹線・特急は通し、1サンプルで数km飛ぶグリッチ（数百 m/s）は落とす。取りこぼしたノイズは Step 2 の精度重みが軽く扱う。区別の本質は「**速いが継続（乗り物）／1点だけ飛んで戻る（グリッチ）**」。より頑健なスパイク検出は [roadmap.md](../roadmap.md) の「温めている案」。

### Step 0: 途切れた区間で分ける

GPS が取れなかった時間帯（長いトンネル・圏外・アプリが止まっていた間）を挟む点どうしは、
**繋がっていないもの**として扱う。`TrackSegments.split` が **3 分**以上空いた所で点列を切り、
平滑化・距離・地図の線は**すべて区間単位**で行う（→ [ADR-0022](../adr/0022-do-not-bridge-gaps.md)）。

分けてから平滑化するのが要点。分けずに窓を回すと、欠落をまたいだ平均が取られ、
何十kmも離れた点どうしが混ざって境目が大きくずれる。距離も、またいで足すと
記録が無い区間の直線距離が「移動した距離」として乗ってしまう。

#### 保存済みの補正点の作り直し

`smoothed_points` は**末尾に足すだけ**で既存の行を書き直さない（記録中の差分INSERT）。
つまり Step 0 より前に記録した経路は、欠落の向こう側と平均された座標を持ったままになる。
窓が5点なら欠落直前の点は向こう側へ 2/5 だけ引き寄せられる（160km の空白なら 64km）。
放っておくと、その架空の移動が**実測の実線**として地図に描かれてしまう。

そこで `TrackSmoother.GENERATION`（平滑化の世代）を持ち、保存済みの点がどの世代で
作られたかを `MaintenanceStore` に覚えておく。古ければ起動時に
`GpsTrackRepository.resmoothGappedTracks()` が**欠落を含む完了済み経路だけ**を作り直す
（距離も焼き直す）。やり切れたときだけ世代を進めるので、途中で落ちても記録中でも
次の起動でやり直される。**立ち寄りは検出し直さない**（手で直したものを壊さないため。
やり直したいときは再解析から → [ADR-0012](../adr/0012-non-destructive-reanalysis.md)）。

差し替えは経路ごとに原子的に行う（`SmoothedPointDao.replaceForTrack`）。消してから入れ直すと、
その間に落ちたとき 0 行のまま残り、次の起動では「欠落なし」と見えて対象から外れてしまう。

作り直しが要る変更を平滑化に入れたら、`GENERATION` を上げること。

### Step 2: 精度重み付き移動平均

各点を、前後 `window` 点の**加重平均**に置き換える。重みは精度の二乗の逆数。

```text
weight_j = 1 / (accuracy_j² + 1)
補正後の位置 = Σ(weight_j × 位置_j) / Σ(weight_j)   （窓の中の点 j について）
```

精度が良い（`accuracy` が小さい）点ほど強く効くので、窓の中に悪い点が混ざっても軽く扱われる。**始点・終点はずらさない**（端点は平均しない）。

## 記録中の補正と保存

補正は**記録中に計算**し、確定した点を `smoothed_points` に保存する。処理は `LocationTrackingService`（GPS取得と同じ場所）が起点。

### 増分計算とラグ

- **Step 1（ジャンプ除外）は直前の採用点だけ見る**ので、新しい点が来た時点でオンラインに判定できる（ラグなし）。
- **Step 2（平滑化）は前後 `window/2`（既定 half=2）点が要る**ので、最新の末尾 `half` 点は**まだ確定できない**。点 `i` は `i + half` が到着した時点で確定し、`smoothed_points` に保存する。
- **ライブ表示**: 確定済みの点は補正後で、末尾の未確定 `half` 点は生（または片側だけの平均）で描く。ラグは既定で2点ぶん（10秒間隔なら約20秒）。
- **記録終了時**: 末尾の未確定点を端点扱いで確定させる。結果は一括バッチ計算（`TrackSmoother.smooth`）と一致する。

**実装**: 新しい点が来るたびに `TrackSmoother.smooth(生点列)` でトラック全体を計算し、**末尾 `half` を除いた確定プレフィックスのうち、まだ保存していない分だけ**を追記する（確定プレフィックスは単調・安定なので通常は1点ずつ増える）。計算はトラック全体だが GPS 間隔では軽く、状態を持たないので中断・再開に強い。書き込みは `GpsTrackRepository.updateSmoothedForTrack(trackId, isFinal)` に集約し、記録中の更新どうしが競合しないよう Mutex で直列化する。呼び出し元は `LocationTrackingService`（点保存後は `isFinal=false`、記録終了時は `isFinal=true`、再開時はキャッチアップ）。

### 保存先: `smoothed_points` テーブル

補正後は生点と**一対一にならない**ため、`gps_points` への列追加ではなく**別テーブル**に持つ。
`removeJumps` がスキップした生点には補正後が存在しないので、**「行の有無」でスキップを自然に表現できる**。

- 列の定義は [../specs/model.md](../specs/model.md) と `SmoothedPointEntity` を正とする。
- `timestamp` は**由来の生点の時刻**を持つ（順序づけと立ち寄り検出で使う）。
- `source_point_id` は由来の生点への参照（トレース用・任意）。DB 上の外部キー制約は張らない。
- Room v2→v3 で追加。`GpsTrack.smoothedPoints` は「読むたびに計算」ではなく
  「保存済みの `smoothed_points` を読む（無ければ生）」。

### 補正を作り直す導線は持たない

保存済みの補正点列をやり直す手段は**提供しない**（[ADR-0012](../adr/0012-non-destructive-reanalysis.md)）。

- 補正パラメータを変えたあとの過去記録への反映は**開発時の一回きりの関心事**。必要ならデバッグ版の
  調整 UI（生↔補正の重ね表示・スライダー）で確認する。
- 立ち寄りのしきい値を変えたときの追加反映は、非破壊の再解析が保存済み補正点列に対して拾う
  （[stops.md](stops.md)）。

## パラメータ（SmoothingParams）

| パラメータ    | 意味                          | 既定 | 大きくすると                                         |
| ------------- | ----------------------------- | ---- | ---------------------------------------------------- |
| `maxSpeedMps` | ジャンプ除外の速度上限（m/s） | 150  | 除外が緩くなる（外れ値が残る）。新幹線を通すため高め |
| `window`      | 平滑窓（ならす点数・奇数）    | 5    | 滑らかになるが実際の角も丸まる                       |

既定値は `TrackSmoother` の定数（`MAX_SPEED_MPS` / `SMOOTHING_WINDOW`）。

### 平滑窓（window）の考え方

「1点をその前後何点と一緒にならすか」の範囲（奇数）。

- **小さい（3）**: 生に忠実。ノイズは少し残るが**実際の曲がり角を保つ**。
- **大きい（9〜）**: とても滑らかだが、**本物の角まで丸めて近道**してしまう。
- **1**: ならさない（＝補正なし）。

窓は**GPS間隔と連動**する。間隔を長くする（点が減る）と、同じ窓でも空間的に広い範囲をならすため強く効く。間隔を変えたら窓も見直す。

## 距離・指標

- **距離**: `TrackSmoother.totalDistanceMeters(points)`。**補正後の点列**で計算するため、ノイズによる膨張が抑えられる。途切れは直線で結んで足す（内訳は `GpsTrack.measuredDistanceMeters` / `bridgedDistanceMeters`）。記録の確定時に一度だけ計算して `gps_tracks.totalDistanceMeters` へ焼き込み、一覧・詳細はその値を読む（→ [ADR-0015](../adr/0015-bake-track-distance.md)）。
- **ジャギーさ**: `TrackSmoother.totalTurningDegrees(points)`。連続区間の進行方向の変化量の合計（度）。ノイズでギザギザだと大きく、補正で下がる。「線の暴れ具合」を数値で比較する指標。

## 調整方法（客観化）

「最適」は真の経路が無い以上多少の判断が残るが、次で客観化する。

1. **調整ツール**（デバッグビルドのみ）: 詳細画面の「調整」トグルで、
   - 生データ（紫）と補正後（橙）を重ねて表示（灰色は欠落を結ぶ破線が使うので避ける）
   - スライダー（速度上限・平滑窓）で地図が即更新
   - 「距離: 生→補正」「曲がり角合計: 生→補正」を数値表示

   実装: `presentation/history/TrackDetailScreen.kt` の `tuningMode` ＋ `TrackTuningPanel.kt`（`BuildConfig.DEBUG` 限定）。

2. **指標の「ひざ」を見る**: 窓を上げると曲がり角合計が下がる。**下げ止まる手前**が「ノイズは取れて実形は残る」塩梅。
3. **正解経路でキャリブレーション（最も客観的）**: 距離が分かる経路を録り、**補正後距離が実測に一致**するよう合わせる。

## GPS間隔との連動

記録間隔は設定で変更可（`data/settings/SettingsRepository.kt`、既定10秒／5・10・30・60秒）。間隔は点密度を決め、補正の効き方（特に窓）に影響する。

## 決めた値の反映

調整ツールで良い値が固まったら、`TrackSmoother` の定数（`MAX_SPEED_MPS` / `SMOOTHING_WINDOW`）に反映する。通常モードの補正（`GpsTrack.smoothedPoints`）は既定パラメータ＝これらの定数を使うため、定数を更新すれば全体に効く。
