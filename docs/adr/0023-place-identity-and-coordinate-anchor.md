# 0023. 場所の同一性は不変なアンカー座標と googlePlaceId で決め、Google の座標は google_places に持つ

- Status: Accepted
- Date: 2026-08-29

関連: 名前の分離は [0001](0001-place-data-separation.md)、ユーザー操作の ID 同定は
[0006](0006-place-identity-by-googleplaceid.md)、座標を Google のものへ置き換える決定は
[0008](0008-registered-places-on-map.md) と [0011](0011-place-coordinate-source.md)、
命名のコスト方針は [0014](0014-place-naming-cost-policy.md)。

## Context（背景）

**同じ場所が大量に重複登録される**。ひとつの敷地で数十〜数百件の place が生まれ、
どれも同じ名前・同じ座標を持つ。

原因は 1 行のバグではなく、**同一性の決め方が成り立っていない**ことにある。

- 同じ場所かどうかは `places` の座標の近さ（30m）で判定している。
- ところが自動命名（`resolvePlace`）が、解決した施設の座標で `places` の座標を**上書きする**。
- 自動命名で使う Nearby Search の半径は 50m なので、施設の代表点はGPS 重心から最大 50m 離れる。
  敷地のある施設（神社・寺・公園・学校・大型商業施設）では実際に離れる（→ [0011](0011-place-coordinate-source.md)）。
- 30m を超えて離れると、**その place は自分を作った重心から見つからなくなる**。次に確保しようと
  すると新しい place ができ、それもまた同じ施設に解決されて同じ座標へ移動する。

つまり**同定に使う鍵を、鍵を使う側が動かしている**。これが本体である。

増殖が桁違いになるのは、記録中の「立ち寄り中」が**位置バッチごと（既定 10 秒ごと）に
`findOrCreatePlace` を呼ぶ**ため。設計上は「滞在中に place を先に確定する」（[stops.md](../designs/stops.md)）
という 1 回の想定だったが、実装は毎ティック探し直している。条件がそろうと 1 時間の滞在で
数百件になり、そのたびに Places も叩かれる（[0014](0014-place-naming-cost-policy.md) の
「place 1 件 1 回」は行単位では守られているが、行が増えるので歯止めにならない）。

座標の上書きは `1ecd35d`（2026-08-08）で入った。それ以前は `resolvePlace` が座標を触らず、
place は重心の上に留まっていたので、毎ティック呼んでも同じ place が再発見されていた。
[0011](0011-place-coordinate-source.md) は「施設の座標が離れていると**次の訪問で**別 place として
検出される余地がある」とこの副作用を認識していたが、**次のティックで**起きることまでは捉えていなかった。

なお名前については v7 で同じ整理を済ませている（`places.name` はユーザーの名前、Google の名前は
`google_places.name`、表示は両者のフォールバック → [0001](0001-place-data-separation.md)）。
**座標だけがその分離から取り残されている。**

## Decision（決定）

**座標も名前と同じ形に分離する。`places` の座標は「アンカー」として不変にし、同定にだけ使う。**

1. **`google_places` に `latitude` / `longitude`（nullable）を持たせる。** Places が `LOCATION` を
   返さないことがあるので null を許す。`places` の座標は従来どおり非 null。
2. **`places` の座標はアンカー**。行を作る瞬間に決まり、**自動処理では二度と書き換えない**。
   `resolvePlace` と `linkPlaceToGoogle` は `places` の座標を更新せず、`google_places` 側に書く。
   アンカーの出どころは行の生まれ方によって違う（GPS 重心／アイコンの座標／施設の座標／ユーザーが
   指した点）。**大事なのは出どころではなく、あとから動かないこと。**
3. **表示・地図のピンは `COALESCE(google_places.latitude, places.latitude)`。**
   施設に紐付いていれば施設の座標に出る。[0011](0011-place-coordinate-source.md) の
   「表示は施設の座標を正とする」はそのまま維持される。
4. **同定は 2 段構え。**
   - まずアンカー座標で近傍（30m）の既存を探す。DB だけで完結し、Places は叩かない。
   - 見つからなければ新規作成して 1 回だけ解決し、**`googlePlaceId` が判明した時点で**
     同じ ID を持つ place があれば**そちらへ統合**する。ID は「検索前の鍵」ではなく
     「解決後の統合キー」なので、API 呼び出しは place 1 件 1 回のまま増えない。
   - **自動統合してよいのは、まだ誰も触っていない `DETECTED` の place だけ。** 自分で付けた名前・
     メモ・行きたい・訪問済みの印が付いた place と `USER` 由来の place は、ID が同じでも自動では
     吸収しない（[0005](0005-place-source-and-lifecycle.md) の「USER は自動で消さない」の延長）。
5. **ひとつの滞在につき place の確保は 1 回。** 記録中のティックごとに `findOrCreatePlace` を
   呼ばず、滞在中は確保済みの placeId を使い回す。
6. **UI の近接確認は表示座標で判定する。** 同定はアンカー、「この近くに登録済みがある」は
   地図に見えているピンとの距離。役目が違うので参照する座標も違う。
7. **`googlePlaceId` の一意制約は後回しにする。** 付ける価値はあるが、(a) 既存の重複を統合してから
   でないと制約の作成自体が失敗する、(b) `@Insert(onConflict = REPLACE)` のままだと衝突相手の行が
   黙って消える、(c) 「強制新規で作った place を、既に他が使っている施設に紐付ける」経路の
   扱いを決める必要がある。まず統合ロジックと通常のインデックス（`getPlaceIdByGoogleId` は
   現在**索引が無く全表走査**）を入れ、データが落ち着いてから検討する。

実装の順序は **2 → 5 → 統合 → 既存データの統合マイグレーション**。2 を入れずに統合だけ足すと、
毎ティック「作っては統合で消す」を繰り返して id を食い、Places も叩き続けるので意味がない。

## Alternatives（検討した没案）

- **同定の半径を広げる（30m → 50m 以上）** … 施設の代表点までの距離をカバーできるが、隣接する
  別の店が混ざる（[0006](0006-place-identity-by-googleplaceid.md) が分離したはずの問題が戻る）。
  鍵が動くという原因も残ったまま → 却下。
- **`places` に「検出座標」列を足して 2 組持つ** … 動作としては成立するが、列が増えるうえ、
  名前でやった分離（ユーザー入力は `places` / Google 由来は `google_places`）と形が揃わない。
  Google の座標が `places` に居座る点も変わらない → 却下。
- **座標の置き換えをやめ、Google の座標を採用しない**（[0011](0011-place-coordinate-source.md) を覆す）
  … 鍵は動かなくなるが、地図のピンが GPS 重心のままになり、Google マップで開いたときや
  経路検索との整合も崩れる。表示の質を落として同定を守るのは筋が悪い → 却下。
- **`googlePlaceId` だけで同定する** … ID を持たない place（POI の無い場所・オフラインで
  未解決・手入力）が同定できない。座標同定は捨てられない → 却下。
- **毎ティックの確保を残したまま、統合で後始末する** … 増殖は見えなくなるが、作っては消すを
  10 秒ごとに繰り返し、id を消費し Places を叩き続ける。原因を隠すだけ → 却下。

## Consequences（結果・トレードオフ）

- 同定の鍵が動かなくなるので増殖が止まる。名前と座標の扱いが同じ形になり、
  「Google 由来は `google_places`」という [0001](0001-place-data-separation.md) の原則が座標にも及ぶ。
- 記録中の Places 呼び出しが「滞在ごとに 1 回」まで落ちる。課金にも効く。
- **既に上書きされてしまった既存行は、元の観測座標が復元できない。** その値をアンカーとして
  固定するだけになる。以後動かないので実害は小さいが、失われたことは記録しておく。
- **アンカーは「その place の現在地」ではなく「最初にそこで確保した」という履歴的な値になる。**
  別の施設に選び直してもアンカーは元の位置に残る。ID を持つ place の同定は ID が優先されるので
  実害は小さいが、意味が変わることは明示しておく。
- **誤解決したときの被害が「並ぶ」から「混ざる」に変わる。** 自動命名は半径 50m の最寄り 1 件しか
  見ないので、別の場所が同じ施設に解決されることがある。今は place が 2 つ残って選び直せるが、
  統合すると融合して分け直しにくい。だから自動統合を「未編集の DETECTED」に限る。
- **表示座標への読み替えは同定以外のすべての読み取りに波及する**（マーカー・近接確認・地図の描画・
  一覧の射影）。実装前に洗い出しが要る。
