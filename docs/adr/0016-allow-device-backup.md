# 0016. 端末の自動バックアップは既定のまま許容する

- Status: Accepted
- Date: 2026-08-15

関連: 約束は [../specs/security.md](../specs/security.md)、実現方法は [../designs/security.md](../designs/security.md)。

## Context（背景）

`android:allowBackup` が既定（`true`）のままで、`backup_rules.xml` /
`data_extraction_rules.xml` はテンプレート（中身が空）のままになっている。
つまり **Room の DB ごと Auto Backup で Google Drive に上がる**。

「データは端末内で完結する」と説明してきたが、厳密にはそうなっていない。
位置情報を扱うアプリとして、意図したのかどうかをはっきりさせる必要があった。

## Decision（決定）

**現状のまま（バックアップを有効のまま）許容する。**

- 上がる先は**本人の Google アカウント**であり、第三者に渡るわけではない。
- 機種変更でお出掛けの記録を引き継げることは、記録アプリとしてむしろ利点になる。
- ローカル DB を暗号化していない現状（[0014 の周辺・設計書参照](../designs/security.md)）と比べて、
  この項目だけを締めても全体の守りは上がらない。

「端末内のみ」という言い方は正確でないので、**仕様書にはバックアップに上がることを明記する**。

## Alternatives（検討した没案）

- **`allowBackup="false"` にする** … 確実に端末内で閉じるが、**機種変更でデータを引き継げなくなる**。
  クラウド同期（Phase 3）が入るまで移行手段が無くなり、失うものの方が大きい → 却下。
- **抽出ルールで DB だけ `<exclude>` する** … 設定は引き継ぎつつ位置情報は上げない折衷案。
  筋は良いが、**引き継げないという結果は同じ**で、ルールの記述と検証の手間だけ増える → 却下。

## Consequences（結果・トレードオフ）

- 端末を紛失しても記録は Drive から復元できる。機種変更も素直に通る。
- **記録が本人の Drive に平文で存在する**。Google アカウントが乗っ取られた場合の被害範囲に含まれる。
- 将来ローカル DB を暗号化するなら、この決定も一緒に見直す（暗号化した DB をそのまま上げても、
  鍵が Keystore にあるため復元先で読めない可能性がある）。
- Phase 3 でクラウド同期を入れると、そちらが正の保管先になるので前提が変わる。
