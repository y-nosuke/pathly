# 0013. 場所・立ち寄り・行きたいを別テーブルに分け、places を静的に保つ

- Status: Accepted
- Date: 2026-07-26（記録は 2026-08-15 に遡って作成）

関連: Google 由来データの分離は [0001](0001-place-data-separation.md)、
場所の由来と自動回収は [0005](0005-place-source-and-lifecycle.md)。

## Context（背景）

「◯◯カフェに 14:40〜15:10 いた」を保存したい。素直に作ると、経路にぶら下がる 1 枚のテーブル
（名前・座標・到着・出発）で足りてしまう。

しかしそれだと、**同じ場所に別の日にまた行ったとき**に困る。行を 2 つ作ることになり、
片方の名前を直しても、もう片方は古い名前のまま残る。「この場所、何回行ったっけ」も数えられない。
さらに、まだ一度も行っていない「行きたい場所」は、経路が無いので置き場所そのものが無い。

## Decision（決定）

**「場所そのもの」と「そこに居たという出来事」を別のテーブルに分ける。**
さらに、**場所に付随する動的な状態は、places に列を足さず別テーブルへ分離する。**

```text
places 1 ──< stops              （立ち寄り＝過去の訪問。place × track）
       1 ──o wishlist           （行きたい＝これからの計画）
       1 ──o place_resolutions  （Google に問い合わせた記録）
       1 ──o google_places      （Google 由来の施設情報）
```

- `places` … 座標と、ユーザーが自分で付けた名前・メモ。**経路から独立**し、静的に保つ。
- `stops` … どの経路で、どの場所に、いつ居たか。経路を消せば消える。
- `wishlist` … 優先度・訪問済み。1 place につき最大 1 件（`placeId` に UNIQUE）。

**判断基準は「場所そのものの性質か、それに付随する状態か」**。前者だけ `places` に置く。

## Alternatives（検討した没案）

- **立ち寄りを 1 枚のテーブルで済ませる**（名前・座標・時刻を同じ行に持つ）… 同じ場所への再訪で
  名前が分裂し、訪問回数も数えられない。行きたい場所を置く先も無い → 却下。
- **`places` に `wantToVisit` / `priority` / `visitedAt` の列を足す** … テーブルは増えないが、
  「計画」という別の関心事が場所そのものに混ざる。同じ理屈で「解決済みか」「カテゴリは何か」も
  足すことになり、places が状態の寄せ集めになる。静的に保つ方針が崩れる → 却下。
- **場所を Google の施設 ID で一意にする**（`googlePlaceId` を主キーにする）… Google が知らない場所
  （空き地・自宅・POI の無い地点）を登録できない。オフラインで完結する、という前提と両立しない → 却下。

## Consequences（結果・トレードオフ）

- 名前を直すと、その場所の**全ての訪問に反映される**。訪問回数も数えられる。
- 行きたい場所は「stops を持たない place」として自然に表現でき、行った後もそのまま同じ place を使える。
- 読み取りが JOIN 前提になる（表示名は `places` と `google_places` を跨いで解決する）。
  射影の行型（`PlaceListItem` / `NamedPlaceRow` など）を用意して吸収している。
- **同じ場所を 2 つ作ってしまう余地**が残る。座標 30m と `googlePlaceId`（[0006](0006-place-identity-by-googleplaceid.md)）で
  同定し、それでも漏れる分は近接確認で気づかせる（[0009](0009-map-tap-behavior.md)）。
- place を消すと `wishlist` / `place_resolutions` / `google_places` は CASCADE で消える。
  逆に stops がある place は消さない（記録を壊さないため）。
