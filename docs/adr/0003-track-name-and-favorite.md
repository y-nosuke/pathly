# 0003. 経路に名前・お気に入りを持たせ、立ち寄り件数は集計で出す（v8）

- Status: Accepted
- Date: 2026-08-07

関連: 現状の仕様は [../specs/tracks.md](../specs/tracks.md)。距離だけ扱いが違う理由は [0015](0015-bake-track-distance.md)。

## Context（背景）

経路（お出掛け＝`gps_tracks`）を「場所」タブと同じように**名前で呼び、お気に入りで拾い、
絞り込み・並べ替え**したい（[../requirements.md](../requirements.md) 2026-08-06 追加）。
一覧カードには**立ち寄った場所の件数**も出したい。名前・お気に入りは経路そのものの属性で、
既存の列だけでは表せない。件数は `stops` から導ける派生値。

## Decision（決定）

- `gps_tracks` に **`name`（TEXT・null=未命名）** と **`isFavorite`（INTEGER NOT NULL DEFAULT 0）** を
  追加する（**DB v8** マイグレーション `MIGRATION_7_8`）。名前は前後空白を除き、空なら未命名（null）に正規化。
- **立ち寄り件数は列に持たない**。`stops` を `GROUP BY trackId` で数えた集計を Flow で流し、
  一覧取得時に `combine` して `GpsTrack.stopCount` に載せる。記録の追加・削除に自動追従する。
- 絞り込み（お気に入り／命名／立ち寄りの 3 軸独立）・並べ替え（日付／立ち寄り数／距離／時間／名前）は
  `HistoryState` の**純関数 `visibleTracks`** で適用する（「場所」タブ `PlacesState.visibleItems` と同型）。

## Alternatives（検討した没案）

- **立ち寄り件数を `gps_tracks` に非正規化列で持つ** … 読みは速いが、立ち寄りの追加・削除・再解析の
  たびに件数を更新する責務が増え、ズレ（バグ）の温床になる。件数は集計で軽く出せる → 却下。
- **名前・お気に入りを別テーブルに切り出す（`track_meta` 等）** … 1 経路 1 行の 1:1 属性を別表にする利点が
  薄く、JOIN と NULL 処理が増えるだけ。`gps_tracks` の列で十分 → 却下。
- **`isFavorite` を `@ColumnInfo(defaultValue = "0")` としてエンティティにも既定を宣言する** …
  マイグレーションの `DEFAULT 0`（既存行のバックフィルに必須）と二重管理になる。エンティティ側に既定を
  宣言しなければ、Room の起動時スキーマ検証は DB 側の DEFAULT を無視するため、宣言しないのが素直 → 却下。
- **お気に入りを絞り込みではなく並べ替え軸にする** … 「お気に入りを先に」よりも「お気に入りだけ見る」需要が
  素直。絞り込み 1 軸として持ち、並べ替えは日付・件数・距離・時間・名前に寄せた → 却下。

## Consequences（結果・トレードオフ）

- 経路を名前で識別でき、お気に入り・立ち寄りの有無・命名状況で素早く絞れる。並べ替えも「場所」と同じ操作感。
- 件数は集計なので**常に正しい**（非正規化のズレが無い）。一覧取得は 2 本の Flow を `combine` する分だけ増えるが、
  件数クエリは軽く、`stops` は小さい。
- 一覧カードの「(N点)」デバッグ表示は「立ち寄り: N件」に置き換えた（GPS 点数は履歴の見出し情報として不要）。
- マイグレーションは列追加のみ（`ALTER TABLE ADD COLUMN`）で破壊なし。`isFavorite` は `NOT NULL DEFAULT 0` で
  既存経路は非お気に入りから始まる。
